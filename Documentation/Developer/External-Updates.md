# External updates, recreation and removal

`internal/recreate` replaces supported standalone containers or complete external Compose projects through the Linux Docker Engine. It does not read or rewrite their Compose source. Managed projects use their stored definition and the [managed update protocol](Managed-Updates.md); Yard uses its dedicated self-update path. Project scheduling remains C5 work.

## Review and supported configuration

The contextual **Update images** and **Recreate containers** actions require an assessment and confirmation. Browser `POST /api/recreate/preview` and `/api/recreate/submit` take `id` (`container:FULL_ID` or `compose:NAME`) and `operation` (`update` or `recreate`); submission also requires `confirm:true` and the current `fingerprint`. Session, Origin and CSRF protections apply. MCP exposes `yard_recreate_preview` and `yard_recreate_submit`. Accepted submissions return a durable job, not a completed replacement. Control API v1 is unchanged.

Preview performs reads only. It returns deployed image identities, container names, running/stopped state, replacement order, preserved setting categories and environment names. Full inspect snapshots, environment values and execution ownership stay private in SQLite. Errors name unsupported settings without exposing their values. Treat SQLite and backups as sensitive.

The assessed contract covers Linux containers with complete inspect/image metadata, standard local bridge or disabled networking, fixed published ports, identifiable local volumes, binds and tmpfs. It preserves command/entrypoint, full environment and labels, user/workdir, healthcheck, restart policy, supported CPU/memory/pids/blkio/ulimit settings, capabilities/security options, read-only roots, standard namespace settings, logging, DNS/hosts, network aliases, explicit IPAM/MAC/driver options and gateway priority. Docker-assigned IP addresses may change. Docker's generated hostname changes with the new container ID; explicit hostnames remain.

Anonymous volume identities are reused, including image-declared volumes; replacements never request volume deletion. Legacy binds are converted to typed mounts preserving effective source, access and propagation. Missing bind sources fail instead of creating empty directories. SELinux bind relabel flags and other legacy flags without a reliable typed representation are refused. Newly pulled images declaring additional volumes are refused before stopping originals; review the deployment source for that change.

Unsupported configured fields are rejected, including auto-removal, legacy links/volumes-from, shared container namespaces, host networking, custom runtimes, device requests, nonlocal volume drivers, nonlocal/overlay/macvlan networks, Swarm tasks, Compose one-offs and dynamic published ports. Paused/restarting/dead/OOM-killed containers and unhealthy running originals must be stabilized first. Groups are limited to 16 containers; configured stop grace must be nonnegative and at most 30 seconds. Unknown configured SDK fields fail assessment rather than being silently dropped.

An external Compose target must have complete service/replica labels. A single member cannot be replaced independently. Observable `depends_on` labels must identify present services with supported started/healthy/completed-successfully conditions and an acyclic order. Incoming container namespace/link/volumes-from references elsewhere on the host block replacement. Source-only relationships, external clients and application-level dependencies cannot be inferred from Docker metadata; use managed source or manual deployment when runtime inspection is insufficient.

## Image comparison and replacement

Update pulls each distinct source reference for the deployed platform and inspects its immutable image ID. Pull failure or a platform mismatch leaves originals intact. No private-registry credential intake is added by C4; registry access must work through the existing Engine pull path. Recreate uses the currently deployed immutable IDs without pulling. Cache-only **Pull images** remains separate.

If every update image is unchanged, the job succeeds with `unchanged`, preserving container identities and state. If any image changes, the whole confirmed group is replaced in dependency order. Fingerprints include configuration, mounts, network identities, running/stopped state and start revision; submission and the worker recheck them before pull and immediately before replacement.

The independent worker uses the exact Yard image with only persistent-state/socket mounts. It records mutation intent before stopping originals in reverse dependency order, renames them to `nox-yard-retained-JOB_ID-ID_PREFIX`, disconnects their endpoints and creates replacements from immutable images in forward order. Originally stopped services remain stopped. Successful one-shot dependencies may execute again. Running targets must remain stable for five seconds and configured healthchecks must be healthy. Verification has a shared two-minute bound within the persisted ten-minute operation deadline, and checks old retained containers plus replacement configuration, images, effective mount sources and endpoint settings.

On ordinary failure, a separate three-minute rollback removes candidates without deleting volumes, restores original names/endpoints and original running/stopped state, then verifies the original container IDs/configuration. A restored update is `failed` / `rolled_back` / `rollback: restored`. Failure or uncertainty during restoration produces `recovery_required`, retains originals/candidates and keeps reservations. Interruption never blindly replays replacement or rollback. The observer can complete an already verified result by read-only verification.

Only verified success allows cleanup of stopped retained originals, without force or volume deletion. Cleanup trouble is separate from replacement outcome. Recovery acknowledgement releases reservations after host review; it deliberately leaves external originals/candidates in place for manual restoration/cleanup. Inspect the private journal and retained names first. Yard reservations coordinate Yard requests; external Docker commands remain outside that coordination.

Standalone jobs reserve old/new IDs and a stable `nox-yard.target` lineage label. Successful completion retargets the job to the new inventory ID. Per-container results include previous/current IDs, service, image/platform, outcome and running/stopped/completed state. Contextual history follows repeated replacements from persisted reservations even when Docker is unavailable.

Replacement does not copy writable container layers or tmpfs contents. Original layers survive until successful cleanup, but are not application persistence. Runtime rollback cannot undo writes or database migrations in shared volumes/binds. Back up application data before replacing applications that migrate it.

## Explicit removal choice and compatibility

Removal dialogs start with volume deletion unchecked. Changing the checkbox reloads the preview and invalidates confirmation. Browser removal preview routes accept `removeVolumes=true|false`; requests and MCP removal tools accept additive `removeVolumes`, defaulting to false. The choice is part of the fingerprint. An omitted flag now retains volumes: this deliberately corrects the previous Engine default. Existing tool names and report shapes remain.

Selecting deletion only makes identifiable, exclusive project-owned or anonymous volumes eligible. Shared volumes, external/unowned named volumes, host binds and Compose source files remain. Project-owned unused networks and image IDs unused by other containers follow the confirmed plan independently of the volume checkbox. Fresh host-wide usage checks precede nonforced volume/network/image deletion. Containers are stopped first; a failed graceful removal can force-remove the specifically confirmed container. Each result distinguishes removed, retained and failed resources.

Managed browser removal submits the reviewed Engine plan through the independent managed worker, then atomically deletes managed metadata after verifying no project containers remain. Managed HTTP/MCP `operation:remove` accepts an optional reviewed fingerprint. Older requests without it are assessed at submission and rechecked by the worker using the same rules; they no longer execute `compose down --volumes`. Pre-C4 persisted remove jobs without an assessment require a fresh request. Empty managed projects can preview/remove owned leftover resources. Partial resource cleanup remains visible after worker cleanup and requires host review.

Generic Engine `yard_project_remove` retains its runtime-only contract, including for a managed project's containers; it does not delete saved managed source metadata. Use `yard_compose_operation` for full managed removal. This distinction preserves the existing adapter response shapes.

## Isolated evidence

`scripts/smoke-recreate.py --image IMAGE` supplies a disposable registry and Linux Go runner. It exercises changed/unchanged images, ports/static networking, configuration and named/anonymous-volume/bind data, failed pull, unsupported new image volumes, stale previews, stopped recreation and dependency-aware partial group rollback without source edits. It also tests real unchecked removal and deliberately deleted fixture originals to prove failed restoration reports unknown state/recovery and retains ownership. `smoke-mcp.py` exercises real independent recreation across web restart, conflicts/history, removal defaults, selected shared-volume protection and managed metadata/source behavior. `smoke-recreate.cjs` checks confirmation/retry/checkbox/outcomes, keyboard/Escape/focus and 1440/768/390/320px layouts.
