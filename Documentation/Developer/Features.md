# Implemented features

This file records current behavior. Future Docker management capabilities are specified in the [Implementation Plan](Implementation-Plan.md).

## First-run administrator and local login

- `GET /api/bootstrap` reports whether setup is needed or a valid session exists. The browser displays setup, login, or the dashboard accordingly.
- `POST /api/setup` creates the only administrator. Username must contain 3–32 ASCII letters, digits, dots, underscores, or hyphens; password must contain 12–128 characters. The database's single administrator row prevents concurrent setup requests from creating two accounts. Setup issues a session on success.
- `POST /api/login` validates the stored Argon2id password. Five failed attempts from one remote IP block further attempts for 15 minutes in the current server process. A successful login clears that IP's attempts.
- Session tokens are random, stored only as SHA-256 hashes in SQLite, and expire after seven days. Cookies are HttpOnly and SameSite Strict. `NOX_PUBLIC_URL` with an HTTPS origin enables a Secure `__Host-` cookie. Browser mutations require an exact Origin match; logout also requires the session CSRF token.
- `POST /api/logout` deletes the session and clears its cookie. `nox-yard reset-admin-password` asks for a new password in an interactive terminal and invalidates all sessions. There is no email or remote password recovery.

Authentication state lives in `data/nox-yard.sqlite`. Keep `data/` persistent and private. The first-run account remains claimable by anyone who can reach the application until setup is completed, so restrict initial network access.

## Application shell

The Go service serves the Vite production build and exposes `/healthz`, which checks SQLite access. The React UI has responsive setup/login screens, a compact dashboard sidebar, and sign-out. UI styles use the semantic tokens in `web/src/styles/tokens.css` and feature CSS Modules.

Settings groups MCP & access, Projects directory and Yard updates into distinct panels with Phosphor headings. MCP is opt-in on a separate port, with a single hashed token shared with Control API, explicit anonymous MCP, inspection/write/sensitive-read permissions and a last-ten-events History modal. Token replacement immediately invalidates its predecessor. Separate Yard/MCP host bindings and ports use persisted pending configuration and explicit Apply now, with optional automatic recreation, durable worker verification and runtime/file recovery. A sidebar MCP indicator opens these settings and represents local server availability. NoX Gateway registration/authentication remains deferred. The directory field and Save action share a row when space permits, with separate examples for new Compose files and exported logs. Update status, last checked and current build use compact wrapping columns. Narrow layouts stack controls inside the shared fullscreen mobile drawer.

## Machine Control API

The opt-in [Control API v1](Control-API.md) exposes inventory, inspection, Engine lifecycle, and image pulls with the shared Yard Bearer token, enforced inspection/write permissions, stable DTOs/errors and application version metadata. Health/info are public on the UI port. Browser sessions, streaming, terminal, managed Compose jobs, and `/healthz` remain independent. Generic managed-project operations require existing containers; machine deploy/editing and CLI onboarding are outside this initial scope.

## Embedded MCP

An opt-in [MCP endpoint](MCP.md) at `/mcp` uses its own listener and loopback-default host port. Yard tokens or explicit anonymous access are configurable in Settings, with execution-time write and sensitive-read checks. Its 35 tools invoke the same application facade and managers as HTTP, including external update/recreate, job/history/recovery tools and the single notifier consumed by browser SSE. The runtime uses a 60-second global timeout; Compose/external-replacement/self-update jobs remain asynchronous. Finite log reads return the last 20 decoded records; interactive terminal and continuous streams retain their existing interfaces. Runtime environment values require an explicit tool invocation; host configuration contents and saved values require an explicit reveal. Configuration tools read and edit current Compose/env files with fingerprint concurrency checks; saving does not alter containers. Tool annotations describe mutation, destructive effects and idempotency; the manual self-update tool explicitly advertises that it can update/restart Yard even with automatic updates disabled.

## Managed Compose and host configuration

URL Sync keeps saved interpolation overrides and declared environment files when their inputs are omitted; explicit replacements can override them. Untouched variable fields are omitted, while edited empty fields are submitted explicitly. Fixed Docker-published port conflicts are reported with the port and owning container during preview and rechecked before replacement, allowing the target project's current ports. This preflight does not reserve ports or detect arbitrary host processes. See [Managed updates](Managed-Updates.md).

The dashboard header has **New Project** beside Refresh. It opens a right-side drawer for a public HTTPS URL, pasted YAML, or an uploaded YAML file. Source intake enforces a 1 MiB limit and public HTTPS destinations. The drawer collects interpolation variables and Compose `env_file` contents, then `POST /api/managed/preview` validates the Compose model and shows a confirmation modal with services, images, ports, mounts, networks, and changes. Builds and unresolved local file dependencies are rejected before deployment. Settings lets the administrator choose an existing base directory on the Docker host. Confirming prepares the directory, pulls, writes initial source/env files and deploys a complete resolved definition with immutable image IDs/platforms. Relative bind mounts resolve against the original project directory. The UI polls the persisted job status. Deploy/copy/adopt/Sync write Compose and environment files, including interpolation values in .env, within the reviewed operation. Successful completion atomically stores file locations and clears active intake contents from metadata; private job snapshots remain available for recovery. There is no background configuration migration. The local development Compose stack runs Vite and the API as separate services, so frontend edits reload at `http://127.0.0.1:5173`.

All projects use **Start**, **Stop**, **Restart**, **Pull** and **Recreate**. Current host Compose/environment files are authoritative. Existing environment fields support inline editing; a collapsed accordion contains the original file editors. Save validates/writes without restarting; Recreate applies saved changes using local images with no build/pull. Configuration is read on demand when opening or explicitly refreshing the drawer. Missing files retain assessed Engine management. See [Configuration files](Configuration-Files.md).

Deploy, sync, Recreate and changed-image updates verify active service replicas through Docker after Compose returns. Existing-container lifecycle actions do not apply or certify saved file changes. Verification is bounded to two minutes within the ten-minute operation deadline. Long-running containers must remain running for five seconds without restarts; configured healthchecks must report healthy. Unexpected exits (including exit zero), dead/OOM-killed containers, unhealthy services and timeouts fail the job. A one-shot service must exit zero and be declared with the service label `nox-yard.lifecycle: oneshot` or a dependency condition `service_completed_successfully`. Inactive profiles and zero replicas are excluded. An unchanged-image result certifies no image change, not pre-existing application health.

Update/sync snapshot supported old runtime/source/env/images and retain rollback image references. Sync preserves old host files/metadata until the candidate passes readiness and immutable-image verification, then commits its journaled files and guarded SQLite result. Ordinary failures restore old images/configuration, source files and original running/stopped state within three minutes. Restored updates remain failed with an explicit restored result; uncertain or failed rollback retains reservations for recovery review. Named volumes and bind contents survive, but application writes, migrations and writable container layers are not undone. Back up migrating applications before replacement. Settings/configuration that cannot be safely assessed are rejected before replacement. See [Managed updates](Managed-Updates.md) for limits, partial initial deployment and source-journal recovery.

Adoption uses the common original Compose working-directory label or asks for the original absolute host directory in the existing preview modal. Conflicting directories are rejected. The directory is persisted, and `compose.yml` plus supplied environment files are created there only when missing; existing files must match byte for byte and symbolic-link paths are rejected. Adoption keeps container IDs and does not restart services. Subsequent Compose operations retain relative-bind bases. Preview/submit fingerprints include source, runtime configuration, local image defaults and file-presence identities. Changed targets/files require a new preview. Comparisons identify added/removed ports, mounts/read-only/propagation, attached networks/aliases, images, command/entrypoint, full environment, labels, user/workdir, healthchecks, restart policy, stop settings, init, declared logging driver/options, tmpfs targets/options/size/mode/read-only state and replica counts without returning secret values. Logging permits inherited daemon defaults; rollback pins and verifies the complete inspected logging configuration. Unsupported comparison settings identify the service/field as a Yard support limitation rather than invalid Compose syntax.

Adoption comparison supports standard attached networks and explicitly named volumes/binds. Anonymous volumes, unavailable local image defaults, unsupported source fields and observable settings such as privileged mode, resource/security overrides, static network options or advanced volume options are rejected before ownership is saved. Proposed images must be present locally; preview never pulls them implicitly. Deployment of a new managed project remains governed by Compose validation rather than this narrower adoption assessment. Temporary managed helpers are hidden from grouped inventory and protected from normal lifecycle, pull and removal actions.

Current Docker labels and saved file locations identify the original directory and ordered Compose filenames. Missing or invalid files are handled by the existing file editors and assessed Engine fallback. There are no migration notices, migration retry actions or periodic migration requests.

Adoption also requires relative bind targets to resolve to the currently mounted host paths. A supplied fallback directory alone is insufficient when those paths differ; adopt matching source first and review later source changes separately. This prevents a valid-looking directory from redirecting existing data on the next Compose operation.

Service config-hash, non-one-off and positive container-number labels must be present so that subsequent Compose operations recognize the adopted containers. A fallback directory does not make arbitrary containers with incomplete Compose identity safe to adopt. One-off containers and Compose hook runners are excluded from runtime verification.

All existing declared env files, including optional `.env`, must be supplied for adoption; otherwise later Compose runs could load unreviewed values from the host. Global `.env` files cannot set `COMPOSE_` or `DOCKER_` controls, matching the restriction on submitted interpolation variables and preserving the default-profile/local-Docker contract. Application variables with those names may use a separate service env file.

## Docker inventory and direct management

`GET /api/projects` requires a valid session. It lists all local Docker containers, groups those with `com.docker.compose.project` labels into Compose projects, and presents other containers individually. Each project includes its containers, state, health, CPU, memory, and uptime. Container details also include image, service name, network totals, and individual metrics. Missing stats are represented as `null`; Docker errors return `503` without blocking login or `/healthz`.

The dashboard supports **Grid** and **List** views with the same project kind, name, state, health, container count, CPU, memory and uptime. List is a semantic table with column headers and approximately 44px rows on every screen size. Its focusable region scrolls horizontally when needed; the page itself does not overflow and rows never stack into cards. The reorder grip remains visible during horizontal scrolling. Search fills the main content width above the header on desktop/tablet and immediately below it on mobile. It filters live by project/container/service name, ignoring case and accents; each whitespace-separated term must match the project's combined names. Container matches retain the whole parent project, never a flattened container card. Search does not change inventory totals or trigger API requests.

The **Sort** menu orders names A to Z or Z to A using natural numeric ordering. Dragging the grip inserts a project at the hovered slot, shifts the intervening projects and previews a blue empty slot plus a floating ghost. Pointer, touch and keyboard reordering share one order across both views; the grip's arrow keys move one position and Home/End move first/last. Escape, pointer cancellation or dropping outside a slot cancels the gesture. With filtered results, only matching projects exchange their existing slots; hidden projects retain theirs. An inventory membership/order change cancels an active gesture, while metric updates preserve it. New projects append alphabetically after the saved manual order; default sorting is A to Z. View, sort and manual order are stored per administrator in this browser/origin under `nox-yard-project-display:<username>`, with a working in-memory fallback if storage is blocked. Search is transient; these preferences do not modify host resources or sync across devices.

The dashboard receives Docker changes through authenticated SSE at `/api/projects/events`, including changes made outside Yard. Event bursts are coalesced for 100 ms. Actions immediately show `starting`, `stopping`, `restarting`, or `removing`, and refresh inventory when their request finishes; managed operations retain their pending state until the job finishes. Manual refresh remains available. Disconnected clients poll every 15 seconds; connected clients reconcile after at least 60 seconds without an inventory refresh. Hidden tabs stop streaming and reconcile when visible again.

Inventory uses only Docker's container list plus grouping, cached metrics, and managed metadata. CPU, memory, and network samples run in the background and are read separately through `/api/metrics`; slow or failed stats never delay inventory. Last successful samples remain available for up to 30 seconds. Uptime is learned from start events, lazy details inspection, or bounded background backfill for containers already running at startup. It may be unknown until that read succeeds; inventory never waits for it. See [Architecture](Architecture.md) for worker bounds.

A Compose project remains Running when its regular services are running and its initializers have exited successfully. Initializers are recognized from deployed `service_completed_successfully` dependency labels or the explicit `nox-yard.lifecycle: oneshot` label, never from service names. Only an exited container with a reported zero exit code is Completed. Failed, unstarted or unknown results continue to count as stopped members; with running services, the project remains Partial. A fully stopped project remains Stopped even if its initializers succeeded. The drawer shows Completed for successful initializers while the underlying Docker state remains `exited`. Detection uses the existing container list, without additional inspection or file reads. Health still comes from Docker healthchecks.

Selecting any Compose card opens the same project overview: immediate actions, aggregate metrics and a compact container list, including projects with just one container. Selecting a container replaces that view with its action row and details; **Back to project** restores the overview. Standalone cards open container details directly. Automatic updates use compact time/save controls beside next/last results, below the primary information; configuration and operation history remain separate sections. Ports and environment fields flow left to right before wrapping into the next row. Values stay masked until revealed.

Project, Settings and New Project drawers share one responsive width: at least 1280px viewport width, `min(50dvw, 60rem)`; from 768px through 1279px, `min(56rem, 100dvw - 2rem)`; below 768px, fullscreen. Project drawers have a fixed header and emphasized Details, Logs, and Terminal tabs. Details scroll independently; logs and terminal fill the remaining height. Close/navigation/disclosure controls use Phosphor icons. Authenticated `GET /api/containers/{id}` inspects the selected container on demand and returns its published and exposed ports, mounts, attached networks, and environment variable names. Values are omitted by default. **Reveal values** uses an Origin- and CSRF-protected `POST /api/containers/{id}/environment`; **Hide values** clears them from the displayed state. Missing containers return 404. The project collection keeps its full width in either view. At viewport widths of 1280px and above, the left sidebar can expand to show labels or collapse to icons, with Settings and the account at its bottom. Below 1280px, mobile, tablet and small desktop use a menu button immediately before Projects to open the expanded sidebar over the page. Outside tap, leftward touch swipe, Escape and the close control dismiss it; canceled/vertical gestures preserve it. Open navigation locks background scrolling and keyboard interaction, receives focus and returns focus to the trigger on dismissal. The desktop collapse preference is preserved, and crossing the navigation breakpoint clears the overlay state.

The Logs tab uses authenticated `GET /api/containers/{id}/logs` with server-sent events. It shows the last 200 Docker log lines, then follows new output from one selected container. TTY and multiplexed stdout/stderr streams are supported. The browser keeps at most 500 lines and closes the stream when the tab, drawer, or browser tab is hidden. Unsupported Docker logging drivers report an unavailable stream.

Search above the log output highlights literal, case-insensitive matches without filtering lines. Previous/next controls and Enter/Shift+Enter navigate matches; Escape clears the search. Highlight/navigation is bounded to 2,000 matches while retaining the complete current buffer. Searching suspends follow-output so results remain readable.

**Export log** below the output captures the current selected container's browser buffer and asks for confirmation. Confirming saves plain UTF-8 text on the Docker host, always under the configured projects base: `BASE/PROJECT_NAME/logs/YYYY-MM-DD-HH-mm.txt`. External Compose projects use this same destination even when their Compose files are elsewhere; standalone containers use `BASE/CONTAINER_NAME/logs`. Missing named directories are created only on export. Compose locations/files remain unchanged. The timestamp uses server time; additional exports in the same minute receive `-02`, `-03`, etc., preserving existing files. Last export reads the newest valid filename in that logs directory and displays its timestamp in the browser's local timezone.

Authenticated `GET /api/projects/{id}/logs/export` reads status without creating directories. `POST` on the same route requires exact Origin, session CSRF, `confirm: true`, the selected member container ID and a nonempty UTF-8 snapshot of at most 8 MiB. No client path is accepted; responses are not cached. A network-isolated helper from Yard's running image mounts only the configured host base, uses confined filesystem access and refuses symbolic-link project/log directories. New directories/files use private permissions and inherit host ownership; completed files are published without overwriting. This requires Yard's container runtime and an accessible configured base, and exports the displayed buffer rather than the entire historical Docker log. Generated `logs/` directories are ignored by Git and Docker build context.

The Terminal tab opens an interactive `/bin/sh` automatically when a running container is selected. A compact reconnect button starts a new session. `GET /api/containers/{id}/terminal` upgrades to a WebSocket after session and exact Origin checks; its first message must include the session CSRF token and a bounded terminal size. Binary frames carry raw TTY input/output; text frames carry open, resize, ready, exit, and error messages. Docker Engine exec runs as the container's configured user, without privileged mode. Leaving the tab or closing the drawer closes the connection. Sessions and command output are not stored. Containers without `/bin/sh` cannot use this terminal.

Opening a terminal checks for `/bin/sh` on demand. The server caches known presence/absence for five minutes and invalidates it on lifecycle changes. Inventory does not probe container filesystems. Missing shells produce an explicit terminal error; an unknown Docker error is not cached as absence.

Project and container drawers provide **Start**, **Stop**, and **Restart** actions. Stop and restart require confirmation. `POST /api/projects/{id}/actions` and `POST /api/containers/{id}/actions` accept `{ "action": "start|stop|restart" }` with a valid session, matching Origin, and CSRF token. Compose group membership is read from current Docker labels before each action; no Compose source file is needed. A group action attempts each eligible container and returns succeeded, skipped, failed, and queued counts plus Docker errors for failures. A stale target returns 404. Stop of Yard itself and manual actions against its temporary helpers are blocked. Restarting Yard queues an independent durable helper from the exact running image ID; it restarts the service, waits for Docker health and persists the result before cleanup. Queued means accepted, and a successful Yard restart does not conceal failures in other group actions.

The Details action row has an overflow menu for **Recreate**, **Pull image(s)** and **Remove**. `POST /api/projects/{id}/pull` reads current host Compose references; a container Pull selects only its Compose service. Standalone targets or missing Compose files use runtime image references. Invalid/inaccessible existing files fail rather than selecting stale references. Pulls update only the local image cache and never replace containers. Public registry images are supported; local-only or private images without available credentials report pull errors. Pulls can take up to ten minutes. Yard exposes Pull/Recreate too, while its Stop/Remove actions and temporary helpers remain protected.

The browser's manual image flow is **Pull → Recreate**; there is no Update menu action. Legacy update APIs and scheduled jobs still pull and compare immutable platform image IDs, preserving containers when unchanged. Recreate uses current host files and cached images; the Engine fallback resolves original references from the local cache, including images previously downloaded by Pull. A secret-safe confirmation shows scope, identities, state, order and preserved setting categories. Engine replacement retains originals, replaces in dependency order and verifies configuration, mounts, networks and readiness. Ordinary Engine failure restores original IDs/configuration/running-stopped state; uncertain recovery holds reservations for host review. Assessed ports, volumes, binds, environment, labels and runtime settings are preserved. Unsupported settings/dependencies receive an explicit reason. Writable layers/tmpfs are not copied and rollback does not undo shared writes/migrations. See [External updates](External-Updates.md) for exact support limits.

Removal opens a confirmation dialog backed by `GET /api/projects/{id}/remove/preview` or `GET /api/containers/{id}/remove/preview`. Volume deletion starts unchecked; changing it reloads the preview (`removeVolumes=true|false`) and invalidates confirmation. The preview lists containers, volumes, networks, images, binds and identifiable source paths. Only **will remove** resources are deleted. Engine POST requests require session, Origin, CSRF and `{ "confirm": true, "fingerprint": "<preview fingerprint>", "removeVolumes": false }`; omitted volume choice defaults false. The backend rechecks the plan and choice before deletion. Containers are stopped first, with a force-removal fallback for the specifically confirmed ID; resource deletion is never forced. Selected exclusive project-owned/anonymous unused volumes may be deleted. Shared/external resources, bind data and source files remain with reasons; per-resource failures remain visible. Managed removal uses the same reviewed plan in its durable worker and deletes saved metadata only after container removal is verified. Cleanup failures survive worker cleanup. Yard/helpers are protected. Unidentifiable resources cannot be discovered by this workflow. See [External updates](External-Updates.md) for older-adapter compatibility and generic runtime-only removal.

## Contextual operation history

Recreate in a container's details selects its Compose service (all replicas) for managed and external projects. The confirmation identifies that scope; dependencies and initializers remain untouched by execution and rollback. Project-level Recreate still covers the whole project. Current Compose/env files and local cached images are used without pull/build, and `image:` plus development `build:` metadata is supported without changing host files. Missing-file Engine fallback retains service scope. See [Configuration files](Configuration-Files.md).

The existing Details drawer has an Operations section with persisted stage/outcome and the latest 30 contextual records, including rollback and cleanup information. Reloading the browser or reopening the drawer restores this state from `GET /api/jobs?target=...`; managed operations and Yard restart survive web-process interruption in independent workers. Shared resource reservations reject overlapping managed/Engine/Yard mutations across browser, MCP and Control API adapters.

An exited worker is verified without replay when possible; otherwise its recovery-required failure keeps actions reserved for host inspection. The drawer requires explicit acknowledgement of that review before releasing the reservation. Acknowledgement changes no containers/files and does not report the failed operation as successful. Unavailable history blocks actions and offers Retry. See [Durable operations](Operation-Jobs.md) for the API, secret handling and recovery procedure.

## Project automatic updates

The project Details drawer provides **Automatic image updates**, disabled by default for managed Compose, external Compose and standalone projects. Enabling requires a supported healthy running target and explicit Save. The drawer shows 03:00, the server timezone, next check and last result. `NOX_TIMEZONE` in Compose configures the server's `TZ` (default `Etc/UTC`); browser timezone never defines the schedule.

Daily checks use immutable image comparison, independent workers, configuration/data preservation, verification and bounded rollback. Stopped, unhealthy, unsupported, absent and helper targets are skipped; Yard uses its dedicated updater through the same daily admission. Missed days become one latest-slot catch-up, with persisted occurrences preventing duplicate execution. Automatic work is serialized; busy/recovery targets have a recorded skip or deferral reason. A known failed image set is suppressed until new images or an explicit manual retry. Scheduled history distinguishes unchanged, skipped, verified, rollback and recovery outcomes. See [Project schedules](Project-Schedules.md) for adapters and recovery.

## Yard self-update

Automatic updates are off by default. The Yard project drawer contains the same file editors, actions and daily schedule as other projects, initially 03:00 in the server timezone with the previous enabled/disabled state preserved. Settings shows only status, last checked, current build and **Check now**, which still checks and installs immediately even when automatic updates are disabled. Independent workers verify startup and restore the previous runtime and SQLite after bounded failure. See [Self-Update](Self-Update.md).
