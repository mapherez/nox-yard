# Implemented features

This file records current behavior. Future Docker management capabilities are specified in the [Implementation Plan](Implementation-Plan.md).

## First-run administrator and local login

- `GET /api/bootstrap` reports whether setup is needed or a valid session exists. The browser displays setup, login, or the dashboard accordingly.
- `POST /api/setup` creates the only administrator. Username must contain 3–32 ASCII letters, digits, dots, underscores, or hyphens; password must contain 12–128 characters. The database's single administrator row prevents concurrent setup requests from creating two accounts. Setup issues a session on success.
- `POST /api/login` validates the stored Argon2id password. Five failed attempts from one remote IP block further attempts for 15 minutes in the current server process. A successful login clears that IP's attempts.
- Session tokens are random, stored only as SHA-256 hashes in SQLite, and expire after seven days. Cookies are HttpOnly and SameSite Strict. `NOX_PUBLIC_URL` with an HTTPS origin enables a Secure `__Host-` cookie. Browser mutations require an exact Origin match; logout also requires the session CSRF token.
- `POST /api/logout` deletes the session and clears its cookie. `nox-yard reset-admin-password` asks for a new password in an interactive terminal and invalidates all sessions. There is no email or remote password recovery.

Authentication state lives in `data/nox-yard.sqlite`. Keep `data/` persistent and private. The first-run account remains claimable by anyone who can reach the application until setup is completed, so restrict initial network access.

## Application shell

The Go service serves the Vite production build and exposes `/healthz`, which checks SQLite access. The React UI has responsive setup/login screens, a compact dashboard sidebar, and sign-out. UI styles use the semantic tokens in `web/src/styles/tokens.css` and feature CSS Modules.

## Machine Control API

The opt-in [Control API v1](Control-API.md) exposes inventory, inspection, Engine lifecycle, and image pulls with independent Bearer authentication, stable DTOs/errors, and application version metadata. Health/info are public on the existing port. Browser sessions, streaming, terminal, managed Compose jobs, and `/healthz` remain independent. Generic managed-project operations require existing containers; machine deploy/editing and CLI onboarding are outside this initial scope.

## Embedded MCP

An always-on, unauthenticated [MCP endpoint](MCP.md) at `/mcp` shares the existing process and port for private homelab LAN clients. Its 30 tools invoke the same application facade and managers as HTTP, including external update/recreate, job/history/recovery tools and the single notifier consumed by browser SSE. The runtime uses a 60-second global timeout; Compose/external-replacement/self-update jobs remain asynchronous. Finite log reads return the last 20 decoded records; interactive terminal and continuous streams retain their existing interfaces. Environment values require an explicit tool invocation. Tool annotations describe mutation, destructive effects and idempotency; the manual self-update tool explicitly advertises that it can update/restart Yard even with automatic updates disabled.

## Docker inventory

The dashboard header has **New Project** beside Refresh. It opens a right-side drawer for a public HTTPS URL, pasted YAML, or an uploaded YAML file. Source intake enforces a 1 MiB limit and public HTTPS destinations. The drawer collects interpolation variables and Compose `env_file` contents, then `POST /api/managed/preview` validates the Compose model and shows a confirmation modal with services, images, ports, mounts, networks, and changes. Builds and unresolved local file dependencies are rejected before deployment. Settings lets the administrator choose an existing base directory on the Docker host. Confirming prepares the directory, pulls, writes initial source/env files and deploys a complete resolved definition with immutable image IDs/platforms. Relative bind mounts resolve against the original project directory. The UI polls the persisted job status. New managed projects store source YAML, variables, source metadata, and their host directory in SQLite. The local development Compose stack runs Vite and the API as separate services, so frontend edits reload at `http://127.0.0.1:5173`.

Managed projects appear in the inventory even when they have no containers. Their existing Details drawer provides Compose start/stop/restart, cache-only pull and **Update images**, plus assessed removal through the managed worker, alongside container logs, inspect and terminal. Update uses saved source without fetching its URL and preserves container IDs/state when the image IDs are unchanged. Repeated source URLs require a confirmed separate copy or source sync; a matching external project can be adopted after a comparison preview. Removal offers an explicit volume deletion choice. Managed operations return a job ID through `/api/managed/jobs/{id}` and persist their final status. Deployment on the Pi has not yet been verified.

Deploy, sync, start, restart and changed-image update verify active service replicas through Docker after Compose returns. Verification is bounded to two minutes within the ten-minute operation deadline. Long-running containers must remain running for five seconds without restarts; configured healthchecks must report healthy. Unexpected exits (including exit zero), dead/OOM-killed containers, unhealthy services and timeouts fail the job. A one-shot service must exit zero and be declared with the service label `nox-yard.lifecycle: oneshot` or a dependency condition `service_completed_successfully`. Inactive profiles and zero replicas are excluded. An unchanged-image result certifies no image change, not pre-existing application health.

Update/sync snapshot supported old runtime/source/env/images and retain rollback image references. Sync preserves old host files/metadata until the candidate passes readiness and immutable-image verification, then commits its journaled files and guarded SQLite result. Ordinary failures restore old images/configuration, source files and original running/stopped state within three minutes. Restored updates remain failed with an explicit restored result; uncertain or failed rollback retains reservations for recovery review. Named volumes and bind contents survive, but application writes, migrations and writable container layers are not undone. Back up migrating applications before replacement. Settings/configuration that cannot be safely assessed are rejected before replacement. See [Managed updates](Managed-Updates.md) for limits, partial initial deployment and source-journal recovery.

Adoption uses the common original Compose working-directory label or asks for the original absolute host directory in the existing preview modal. Conflicting directories are rejected. The directory is persisted, and `compose.yml` plus supplied environment files are created there only when missing; existing files must match byte for byte and symbolic-link paths are rejected. Adoption keeps container IDs and does not restart services. Subsequent Compose operations retain relative-bind bases. Preview/submit fingerprints include source, runtime configuration, local image defaults and file-presence identities. Changed targets/files require a new preview. Comparisons identify added/removed ports, mounts/read-only/propagation, attached networks/aliases, images, command/entrypoint, full environment, labels, user/workdir, healthchecks, restart policy, stop settings and replica counts without returning secret values.

Adoption comparison supports standard attached networks and explicitly named volumes/binds. Anonymous volumes, unavailable local image defaults, unsupported source fields and observable settings such as privileged mode, resource/security overrides, static network options or advanced volume options are rejected before ownership is saved. Proposed images must be present locally; preview never pulls them implicitly. Deployment of a new managed project remains governed by Compose validation rather than this narrower adoption assessment. Temporary managed helpers are hidden from grouped inventory and protected from normal lifecycle, pull and removal actions.

Legacy managed records without a saved host directory cannot start, restart, update or sync through an invented temporary directory: those operations report a directory-recovery error. Recovery/migration of such prior adoptions remains an upgrade-acceptance item. New adoptions always persist their verified directory. Sync fingerprints also reflect the saved project record and current runtime; shared resource reservations prevent conflicting managed/Engine/Yard mutations across adapters.

Adoption also requires relative bind targets to resolve to the currently mounted host paths. A supplied fallback directory alone is insufficient when those paths differ; adopt matching source first and review later source changes separately. This prevents a valid-looking directory from redirecting existing data on the next Compose operation.

Service config-hash, non-one-off and positive container-number labels must be present so that subsequent Compose operations recognize the adopted containers. A fallback directory does not make arbitrary containers with incomplete Compose identity safe to adopt. One-off containers and Compose hook runners are excluded from runtime verification.

All existing declared env files, including optional `.env`, must be supplied for adoption; otherwise later Compose runs could load unreviewed values from the host. Global `.env` files cannot set `COMPOSE_` or `DOCKER_` controls, matching the restriction on submitted interpolation variables and preserving the default-profile/local-Docker contract. Application variables with those names may use a separate service env file.

`GET /api/projects` requires a valid session. It lists all local Docker containers, groups those with `com.docker.compose.project` labels into Compose projects, and presents other containers individually. Each project includes its containers, state, health, CPU, memory, and uptime. Container details also include image, service name, network totals, and individual metrics. Missing stats are represented as `null`; Docker errors return `503` without blocking login or `/healthz`.

The dashboard receives Docker changes through authenticated SSE at `/api/projects/events`, including changes made outside NoX Yard. Event bursts are coalesced for 100 ms. Actions immediately show `starting`, `stopping`, `restarting`, or `removing`, and refresh inventory when their request finishes; managed operations retain their pending state until the job finishes. Manual refresh remains available. Disconnected clients poll every 15 seconds; connected clients reconcile after at least 60 seconds without an inventory refresh. Hidden tabs stop streaming and reconcile when visible again.

Inventory uses only Docker's container list plus grouping, cached metrics, and managed metadata. CPU, memory, and network samples run in the background and are read separately through `/api/metrics`; slow or failed stats never delay inventory. Last successful samples remain available for up to 30 seconds. Uptime is known after an observed start event or a lazy details inspection; already-running containers show unknown uptime after backend startup until one of those occurs.

Selecting a Compose card opens a right drawer with one project action row, a summary, and a compact container list. Selecting a container replaces that view with its action row and details; **Back to project** restores the list. A project with one container opens that container's details immediately. The drawer has a fixed header and Details, Logs, and Terminal tabs. Only the tab content scrolls. Authenticated `GET /api/containers/{id}` inspects the selected container on demand and returns its published and exposed ports, mounts, attached networks, and environment variable names. Values are omitted by default. **Reveal values** uses an Origin- and CSRF-protected `POST /api/containers/{id}/environment`; **Hide values** clears them from the displayed state. Missing containers return 404. The project grid keeps its full width. The left sidebar can expand to show labels or collapse to icons on desktop and tablet, with Settings and the account at its bottom. Mobile uses a menu button to open the wide sidebar over the page.

The Logs tab uses authenticated `GET /api/containers/{id}/logs` with server-sent events. It shows the last 200 Docker log lines, then follows new output from one selected container. TTY and multiplexed stdout/stderr streams are supported. The browser keeps at most 500 lines and closes the stream when the tab, drawer, or browser tab is hidden. Unsupported Docker logging drivers report an unavailable stream.

The Terminal tab opens an interactive `/bin/sh` automatically when a running container is selected. A compact reconnect button starts a new session. `GET /api/containers/{id}/terminal` upgrades to a WebSocket after session and exact Origin checks; its first message must include the session CSRF token and a bounded terminal size. Binary frames carry raw TTY input/output; text frames carry open, resize, ready, exit, and error messages. Docker Engine exec runs as the container's configured user, without privileged mode. Leaving the tab or closing the drawer closes the connection. Sessions and command output are not stored. Containers without `/bin/sh` cannot use this terminal.

Opening a terminal checks for `/bin/sh` on demand. The server caches known presence/absence for five minutes and invalidates it on lifecycle changes. Inventory does not probe container filesystems. Missing shells produce an explicit terminal error; an unknown Docker error is not cached as absence.

Project and container drawers provide **Start**, **Stop**, and **Restart** actions. Stop and restart require confirmation. `POST /api/projects/{id}/actions` and `POST /api/containers/{id}/actions` accept `{ "action": "start|stop|restart" }` with a valid session, matching Origin, and CSRF token. Compose group membership is read from current Docker labels before each action; no Compose source file is needed. A group action attempts each eligible container and returns succeeded, skipped, failed, and queued counts plus Docker errors for failures. A stale target returns 404. Stop of NoX Yard itself and manual actions against its temporary helpers are blocked. Restarting NoX Yard queues an independent durable helper from the exact running image ID; it restarts the service, waits for Docker health and persists the result before cleanup. Queued means accepted, and a successful Yard restart does not conceal failures in other group actions.

The Details action row has an overflow menu for **Pull image(s)** and **Remove**. `POST /api/projects/{id}/pull` and `POST /api/containers/{id}/pull` pull the image references recorded in Docker; project pulls deduplicate shared references. Pulls only update the local image cache and do not recreate running containers. Public registry images are supported; local-only or private images without credentials report pull errors. Pulls can take up to ten minutes and return per-image successes and errors. NoX Yard uses its separate self-update path, so these menu actions are disabled for its own container.

Standalone and complete external Compose targets offer **Update images** and **Recreate containers** in their existing contextual menus. A secret-safe assessment/confirmation shows deployed identities, state, order and preserved setting categories. Updates compare pulled immutable platform image IDs and preserve containers when unchanged; recreate uses deployed IDs without pulling. Changed groups retain originals, replace in dependency order and verify configuration, mounts, networks and readiness. Ordinary failure restores original IDs/configuration/running-stopped state; uncertain recovery holds reservations for host review. Ports, named/anonymous volumes, binds, environment, labels, command/user, resource/security settings and assessed endpoints are preserved. Unsupported configured fields/dependencies receive an explicit reason. Writable layers/tmpfs are not copied and rollback does not undo shared writes/migrations. See [External updates](External-Updates.md) for the exact support limits and recovery contract.

Removal opens a confirmation dialog backed by `GET /api/projects/{id}/remove/preview` or `GET /api/containers/{id}/remove/preview`. Volume deletion starts unchecked; changing it reloads the preview (`removeVolumes=true|false`) and invalidates confirmation. The preview lists containers, volumes, networks, images, binds and identifiable source paths. Only **will remove** resources are deleted. Engine POST requests require session, Origin, CSRF and `{ "confirm": true, "fingerprint": "<preview fingerprint>", "removeVolumes": false }`; omitted volume choice defaults false. The backend rechecks the plan and choice before deletion. Containers are stopped first, with a force-removal fallback for the specifically confirmed ID; resource deletion is never forced. Selected exclusive project-owned/anonymous unused volumes may be deleted. Shared/external resources, bind data and source files remain with reasons; per-resource failures remain visible. Managed removal uses the same reviewed plan in its durable worker and deletes saved metadata only after container removal is verified. Cleanup failures survive worker cleanup. NoX Yard/helpers are protected. Unidentifiable resources cannot be discovered by this workflow. See [External updates](External-Updates.md) for older-adapter compatibility and generic runtime-only removal.

## Contextual operation history

The existing Details drawer has an Operations section with persisted stage/outcome and the latest 30 contextual records, including rollback and cleanup information. Reloading the browser or reopening the drawer restores this state from `GET /api/jobs?target=...`; managed operations and Yard restart survive web-process interruption in independent workers. Shared resource reservations reject overlapping managed/Engine/Yard mutations across browser, MCP and Control API adapters.

An exited worker is verified without replay when possible; otherwise its recovery-required failure keeps actions reserved for host inspection. The drawer requires explicit acknowledgement of that review before releasing the reservation. Acknowledgement changes no containers/files and does not report the failed operation as successful. Unavailable history blocks actions and offers Retry. See [Durable operations](Operation-Jobs.md) for the API, secret handling and recovery procedure.

## NoX Yard self-update

Automatic updates are off by default. The Settings drawer controls them and their check interval, and shows status and build details. The updater compares the running image ID with the platform image ID behind GHCR `latest`, then uses a temporary worker to replace NoX Yard and restore the previous container and SQLite snapshot if the replacement fails health. See [Self-Update](Self-Update.md) for the operational contract.
